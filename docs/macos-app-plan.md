# macOS 앱 작업 계획

작성일: 2026-09-14. 상태: 기본 앱과 창·메뉴·링크를 stacked draft PR로 구현 중이다. 별도 연결 복구 UI는 초기 범위에서 제외했다. 로그인 연결·계정 가입·공개 배포는 아직 진행하지 않았다. 실행 방법과 검증 범위는 [macOS 앱 개발](macos-development.md)을 참고한다.

## 1. 목표와 전제

기존 채소ZIP 웹의 추천·비교·시뮬레이션·저장 결과 흐름을 macOS 앱에서 제공한다.

- 확정: macOS 전용, Apple Silicon 우선, 첫 버전은 기존 웹 기능만 제공.
- 확정: 앱 표시 이름과 아이콘은 기존 웹의 서비스 이름·로고를 재사용한다. 원본 자산을 확인하고 macOS 앱 아이콘 규격에 맞게 준비한다.
- 제안: 현재 저장소에 `src-tauri/` 추가. 별도 모노레포 도구나 프런트엔드 분리 없음.
- 제안: Tauri 2 WebView에서 배포된 HTTPS Next.js 웹을 로딩. Next.js BFF와 서버 배포 유지.
- 확정: Mac App Store는 이후 검토. 첫 배포는 DMG 직접 배포를 기본안으로 한다.
- 확정: 앱을 새로 실행하면 기존 홈(`/`)에서 시작한다. 빨간 닫기 버튼은 창만 닫고, Dock 클릭으로 다시 열며, `⌘Q`는 앱을 종료한다.
- 기본안: 창을 닫았다 다시 열 때 현재 화면을 유지하도록 단일 창을 숨김/표시한다. 앱 프로세스를 완전히 종료한 뒤 실행하면 홈으로 간다.
- 확정: 초기 테스트는 새 DMG를 내려받아 수동 교체한다. 일반 사용자 배포부터 Tauri updater를 통해 앱 안에서 업데이트를 안내하고 사용자가 설치할 수 있도록 한다.
- Homebrew·TestFlight·스토어용 빌드·Apple 로그인은 첫 버전 범위에서 제외한다.
- 웹 배포는 기존 흐름을 유지하되, 구버전 앱 호환성을 고려한다.
- 확정: 네트워크 연결을 전제로 한다. 첫 버전은 별도 로컬 로딩·오프라인 오류 화면과 연결 감시 타이머를 제공하지 않는다. 웹이 열린 뒤의 오류는 기존 웹에서 처리한다.

전담 기획자 없이 진행할 수 있다. 사용자는 대상 사용자·제품 가치·범위·출시 여부를 결정하고,
개발 과정에서 요구사항·예외 흐름·완료 조건·출시 자료를 함께 문서화한다.
인증 서버 변경은 백엔드 담당과 협의한다. 사용자가 웹·앱 동시 로그인 정책을 문의했으며 답변을 기다리는 중이다.
Apple 계정·서명·외부 배포 책임자는 배포 준비 시 지정한다.

## 2. 현재 코드에서 확인한 조건

| 근거 | 계획에 미치는 영향 |
| --- | --- |
| `next.config.ts`: `output: 'standalone'` | 정적 export로 변경하지 않고 기존 서버를 유지한다. |
| `docs/auth.md`: Next.js BFF, HttpOnly 쿠키 | 앱에서도 서비스 토큰을 브라우저 JS에 노출하지 않는다. |
| `src/pages/auth/auth-entry/model/use-google-auth-flow.ts` | Google 웹 인증은 외부 브라우저에서 재사용하는 방향을 검증한다. |
| `src/app/api-routes/auth/route-utils.ts` | 실제 WKWebView의 Origin·Sec-Fetch-Site와 기존 출처 검사 호환성을 확인한다. |
| `src/shared/lib/auth/session.ts` | 브라우저·앱 세션을 무작정 복제하지 않고 refresh 회전 정책을 확인한다. |
| PostHog rewrite·Sentry tunnel | 기존 관측 도구를 재사용하고 앱 버전·OS 정보를 보강한다. |

개발 Mac에서 WKWebView 실행, 로컬 홈·세션 API 응답, Apple Silicon용 앱·DMG 빌드를 확인했다. 쿠키 유지·외부 인증 복귀·전체 화면 흐름과 최소 OS 호환성은 아직 검증하지 않았다.
Next.js 코드를 구현하기 전 설치된 패키지의 `node_modules/next/dist/docs/`에서 관련 가이드를 읽는다.
온라인 예제의 버전과 현재 프로젝트의 Next.js 버전 차이를 확인한다.

## 3. 남은 확인사항과 결정 시점

| 결정 | 제안 또는 확인할 내용 | 결정 시점 |
| --- | --- | --- |
| 최소 macOS | 미정. 실제 사용자 OS, 사용하는 웹 기능·네이티브 플러그인 요구사항, 대상 OS의 WKWebView 검증으로 결정. Sonoma 필수 근거는 아직 없음 | 1~4단계 |
| 배포 파일 제공 위치 | 웹사이트에서 다운로드, 파일은 GitHub Releases 또는 기존 저장소/CDN에 호스팅 | 외부 배포 전 |
| 앱 식별자 | 기존 서비스 도메인 기준으로 Bundle ID·앱 복귀 scheme을 정하고 중복을 확인. 표시 이름·아이콘은 기존 브랜드 재사용으로 확정 | 기본 앱 구현 시 |
| 배포 계정·연락처 | Apple 개인/조직 계정과 서명·배포 담당, 지원 연락처 | 일반 사용자 배포 전 |
| 인증 서버 지원 | 동시 로그인 문의 답변 대기. 앱용 독립 세션 발급, 로그아웃 범위, 일회용 코드 저장소 확인 | 2단계 전 |
| 서버 도메인 | 운영·스테이징 URL과 허용 origin을 실제 환경 기준으로 확인 | 1단계 전 |

현재 결정된 내용으로 기본 앱 구현을 시작할 수 있다. 창 크기·기본 메뉴·기술적 식별자는 기존 코드와 도메인을 확인해 구현 과정에서 정리한다.
인증 정책 답변은 인증 작업에 반영하고, 최소 OS·다운로드 호스팅·서명 계정은 해당 단계에서 확정한다.

## 4. 단계별 작업과 완료 조건

### 0단계 — 첫 배포 범위 정리

- 한 장 분량의 제품 명세 작성: 대상 사용자, 앱 가치, 첫 출시 기능, 제외 기능, 핵심 사용자 흐름.
- 기존 웹 기능과 앱 기본 동작만 범위에 포함한다. 결과 내보내기·공유·알림·메뉴바 상주 등 신규 제품 기능은 추가하지 않는다.
- Google·이메일 로그인과 기존 계정 삭제 흐름을 유지한다. 앱 때문에 새로 수집하는 정보가 있으면 기존 개인정보 안내에 반영한다.
- Tailwind v4의 기본 Safari 요구사항은 16.4 이상이다. 이것만으로 앱 전체 호환성이 보장되지는 않는다.
- Tauri는 macOS의 WKWebView를 사용하므로 최소 버전은 CPU 종류와 별개로 결정한다. 앞서 제안한 macOS 14는 지원 범위를 좁히기 위한 후보였으며 기술적 하한으로 입증되지 않았다. 최소 버전은 미정으로 둔다.
- Tailwind의 Safari 16.4 요구사항만으로 macOS 14 이상을 도출할 수 없다. Safari 16.4는 Ventura 13.3에도 제공되었다. 설치된 Safari 버전만으로 앱의 WKWebView 호환성을 단정하지 않는다.
- 현재 개발 Mac은 macOS 26.5.2로 확인했다. 먼저 이 환경에서 PoC를 진행하고 초기 사용자의 OS를 파악해 하위 버전 검증 범위를 정한다. 지원을 선언하는 최소 OS·패치에서는 실제 앱을 검증한다.
- 사용자 계정 준비와 기술 PoC는 독립적으로 진행할 수 있다. 계정 미가입만으로 로컬 검증을 미루지 않는다.

완료 조건: 기존 웹 기능, 앱 기본 동작, 첫 배포 방식과 남은 결정이 기록되어 있다.

### 1단계 — Tauri 기본 앱 PoC

- 루트에 `src-tauri/`를 추가하고 Rust 의존성은 Cargo로 관리한다.
- 기존 Node 24·pnpm 11.4 설정 유지. Tauri 개발·빌드 스크립트는 `node --run <script>` 형태로 추가한다.
- 로컬 Next.js와 스테이징 웹을 각각 열어 확인한다. 개발 서버는 기존 Doppler·포트 규칙을 따른다.
- 직접 배포에 맞는 서명·권한 설정을 사용한다. App Store용 App Sandbox는 이번 PoC의 필수 조건으로 두지 않는다. Tauri capability 제한과 macOS App Sandbox는 별개다.
- 단일 창, 기본 크기·최소 크기, 제목, 아이콘과 기본 메뉴를 구성한다. 최초/완전 재실행 시 홈으로 진입한다.
- 운영 도메인만 앱 안에서 열고 외부 URL은 검증 후 기본 브라우저로 연다.
- 네이티브 API 권한은 필요한 명령·URL 범위로 제한한다. 앱에서 임의 명령 실행이나 전체 파일 접근을 허용하지 않는다.
- 기존 웹 홈으로 바로 접속한다. 최초 접속 실패는 웹의 `global-error`로 보장할 수 없으며, 자체 안내 화면은 후속 과제로 남긴다. 연결 복구 후 홈 이동 메뉴로 다시 접속할 수 있게 한다.

완료 조건: 설치된 앱에서 핵심 웹 화면과 일반 API가 동작하고, 외부 링크·창 재열기·홈 재접속 동작을 확인한다.

### 2단계 — 외부 브라우저 로그인과 앱 세션 연결

사용자 흐름:

```text
앱에서 로그인 시작
  → 기본 브라우저에서 서비스 로그인 페이지 열기
  → Google/이메일 인증 및 필요한 가입·계정 연결 완료
  → 현재 계정을 확인하고 앱 로그인 승인
  → 앱 전용 링크로 복귀
  → 앱 WebView가 BFF에서 일회용 코드 교환
  → HttpOnly 세션 쿠키 설정 후 원래 화면 복귀
```

- 먼저 서버 계약을 확정한다. 앱 세션은 웹 브라우저 세션과 독립적으로 발급하는 것을 목표로 한다.
- 기존 브라우저 세션의 refresh token을 앱 쿠키로 복사하지 않는다. 기존 API가 독립 세션 발급을 지원하지 않으면 백엔드 변경 또는 앱 전용 재인증 흐름을 먼저 마련한다.
- 로그인 시작마다 검증값을 생성하고 challenge를 서버 요청에 연결한다. state와 교환 시 verifier를 검사해 코드를 가로챈 다른 앱이 교환하지 못하도록 한다.
- 서버 코드는 짧게 만료되며 원자적으로 한 번만 소비한다. 서버 재시작·다중 인스턴스를 고려한 공유 저장소와 TTL을 결정한다.
- 전용 URI scheme은 앱 복귀용이다. Google의 redirect URI를 이 scheme으로 바꿀 필요가 있다고 가정하지 않는다.
- 고정된 callback 경로, 허용된 return path, 진행 중인 로그인 요청을 검증한다.
- access/refresh token은 딥링크·로그·분석 이벤트에 넣지 않는다. 코드·검증값도 관측 도구에서 제외한다.
- 마지막 교환 요청은 WebView에서 same-origin BFF로 보내고, 응답의 Set-Cookie로 세션을 설정한다.
- 기존 BFF 출처 검사는 유지한다. WebView 호환 문제가 있으면 증거를 수집하고 같은 보안 목적을 유지하는 좁은 수정안을 검토한다.
- 앱 실행 중 복귀와 앱이 종료된 상태에서의 복귀를 모두 처리한다. 종료로 검증값을 잃은 경우 안전하게 로그인을 다시 시작하도록 정의한다.
- 외부 브라우저 로그인 취소·앱 열기 거부·코드 만료 시 안내와 재시작을 제공한다.

완료 조건:

- 기존 사용자 로그인, 신규 가입, 계정 연결, 취소, 만료, 중복 콜백을 검증했다.
- 변조된 state/verifier, 재사용 코드, 허용되지 않은 경로를 거부한다.
- 앱 재실행·절전 복귀 후 로그인 상태가 일치한다.
- 브라우저와 앱을 함께 사용해도 refresh 회전이 충돌하지 않는다.
- 앱/브라우저 로그아웃의 영향 범위가 정의대로 동작한다.

macOS 딥링크는 번들 앱을 `/Applications`에 설치해서 검증한다. 개발 서버에서 화면이 열리는 것만으로 완료하지 않는다.

### 3단계 — 기존 웹을 위한 macOS 기본 동작

- 빨간 닫기 버튼은 창만 숨기고, Dock 클릭은 기존 창을 다시 표시한다. `⌘Q`는 프로세스를 종료한다. 닫힌 동안 불필요한 폴링·애니메이션은 쉬도록 확인한다.
- macOS 기본 제목 표시줄과 최소화·확대/전체 화면·크기 변경 동작을 사용한다. 창 최소 크기는 기존 웹 반응형 레이아웃을 보고 정한다.
- 복사·붙여넣기·실행 취소·종료 등 기본 메뉴와 키보드 동작을 확인한다.
- 화면 맨 위 macOS 메뉴 막대에 앱 정보·숨기기·종료, 편집, 윈도우 항목을 둔다. 메뉴바 상주 아이콘은 추가하지 않는다.
- 서비스 내 링크는 앱에서 이동하고, 타 사이트와 새 창 요청은 URL 정책에 따라 기본 브라우저로 연다. Google 인증도 외부 브라우저를 사용한다.
- 추천·비교·시뮬레이션·저장 결과·마이페이지의 실제 핵심 경로를 검증한다.
- 서버 장애, 로딩 지연, 세션 만료 후 재로그인에서 사용자에게 다음 행동을 안내한다.
- 네이티브 연결부는 `src/shared/lib`의 작은 인터페이스로 두고, 도메인 행동은 `features`/`pages`, 조립과 BFF는 `src/app`에 둔다.
- 일반 브라우저에는 앱 전용 호출이 요구되지 않도록 대체 동작을 유지한다.

완료 조건: 기존 웹 기능을 키보드와 창 조작으로 사용할 수 있고, 홈 진입·창 재열기·외부 링크 처리가 정의대로 동작한다.

### 4단계 — 품질·운영 검증

- 선택한 최소 macOS 및 지원 아키텍처에서 설치·실행·로그인·종료·재실행을 확인한다.
- WKWebView에서 차트·애니메이션·한국어 입력·포커스·스크롤을 검증한다.
- 인증 코드 교환은 만료·재사용·동시 요청·위조를 포함한 회귀 테스트를 작성한다.
- 기존 웹 변경에 대해 `node --run fmt:check`, `node --run lint`, `node --run test:ci -- --project unit`, `node --run build`를 실행한다. 셸 Node 버전이 다르면 `mise exec --`를 앞에 붙인다.
- Rust 변경에는 `cargo fmt --check`, `cargo clippy`, 해당 로직의 테스트와 macOS 번들 빌드를 적용한다.
- 기존 Sentry·PostHog를 재사용하고 앱 버전·웹 릴리스·OS로 문제를 구별한다. 네이티브 오류 수집 범위도 정의한다.
- 웹이 구버전 앱의 지원 기능을 확인할 수 있도록 브리지 버전·capability 계약과 대체 동작을 둔다. 이를 인증 근거로 사용하지 않는다.

완료 조건: 핵심 사용자 흐름, 보안 회귀, 일반 웹 회귀, 설치 빌드 검증이 통과하고 최소 OS 검증 결과와 알려진 제한이 기록되어 있다.

### 5단계 — DMG 직접 배포 준비

- 로컬 개발과 ad-hoc 서명 DMG 생성은 유료 개발자 가입 없이 진행한다.
- 일반 사용자 배포용으로 Apple Developer Program, Developer ID 서명과 공증을 준비한다. 이는 App Store 심사와 별개다.
- Apple Silicon용 DMG를 생성하고 설치·앱 교체·쿠키 유지·딥링크를 검증한다.
- CI 자동화 시 인증서·키는 Doppler 등 기존 시크릿 관리 경로로 공급하고 저장소에 넣지 않는다.
- 다운로드 페이지에 Apple Silicon, 실제 검증한 최소 macOS, 버전, 설치 방법과 지원 연락처를 표시한다.
- 초기 테스트 빌드는 DMG 수동 교체로 배포한다. 앱 내 업데이트 구현이 초기 PoC의 선행 조건은 아니다.
- 일반 사용자 배포 전에 Tauri updater 서명·업데이트 파일·manifest를 구성한다. updater 서명은 Apple 코드 서명과 별개로 관리한다.
- 앱에서 새 버전을 안내하고 사용자 확인 후 설치·재시작한다. 업데이트 실패 후 기존 버전 사용과 DMG 수동 교체가 가능한지 검증한다.
- 배포 직전 구현·검증 결과와 알려진 문제를 검토한다.

완료 조건: 일반 사용자용 서명·공증된 DMG, 다운로드 안내, 앱 내 업데이트가 준비되고 실제 설치·업데이트·배포 링크를 검증했다.

## 5. 작업 분할과 진행 순서

문서 PR을 `main` 대상으로 먼저 올리고, 구현은 부모 브랜치를 base로 하는 stacked draft PR로 분리한다.
각 PR의 diff는 부모 PR에 추가되는 변경만 검토한다. 현재 문서 PR에는 구현 코드를 포함하지 않는다.

| PR | 범위 | 부모 | 예상 파일 수 | 예상 변경 줄 수 |
| --- | --- | --- | --- | --- |
| 0. 계획 문서 | 확정 범위·미정 사항·검증 기준·Moa 참고 | main | 1 | 약 230 |
| 1. Tauri 기본 앱 | Rust/CLI 설정, 로컬·배포 웹 연결, 브랜드 아이콘, Apple Silicon 개발용 DMG | PR 0 | 8~12 | 200~400 |
| 2. 창·메뉴·탐색 | 창 숨김/재열기, 기본 메뉴, 외부 URL 정책, 홈 직접 접속, 관련 검증 | PR 1 | 5~9 | 250~500 |
| 3. 인증 BFF | 서버 계약 확정 후 앱 세션·일회용 코드 발급/교환·회귀 테스트 | PR 2 | 5~10 | 400~800 |
| 4. 앱 로그인 연결 | 브라우저 로그인 진입, 딥링크, WebView 쿠키 교환, 가입·취소·만료 흐름 | PR 3 | 5~9 | 300~600 |
| 5. 배포·업데이트 | Developer ID 서명·공증, CI, 업데이트 안내/설치, 다운로드 안내 | PR 2에서 별도 분기 | 3~6 | 200~400 |

예상치는 추가+삭제 줄 수이며 직접 작성하는 코드·설정·테스트·문서 기준이다. 같은 파일을 여러 PR에서 수정할 수 있어 파일 수를 합산해 전체 파일 수로 해석하지 않는다.
`Cargo.lock`, `pnpm-lock.yaml`, 자동 생성 파일과 아이콘 바이너리는 제외한다. 특히 최초 Cargo 의존성 도입으로 전체 diff는 수천 줄 더 커질 수 있다.
구현 PR 합계는 대략 1,350~2,700줄로 예상하되, 인증 서버 계약·코드 저장소·플러그인 동작에 따라 달라진다. 백엔드 저장소 변경은 이 추정에 포함하지 않는다.

첫 작업은 PR 1~2까지로 제한한다. 합계 약 450~900줄이며, 로그인 기능의 완성을 기다리지 않고 설치·홈 탐색·창 동작·외부 링크를 검증한다.
PR 1은 빌드와 홈 로딩, PR 2는 앱 기본 동작 전체를 완료 조건으로 삼는다. 초기 테스트에서는 DMG를 수동 교체한다.
PR 5는 인증 답변을 기다리지 않고 준비할 수 있지만 일반 사용자 배포는 PR 4까지 통합한 로그인·업데이트 검증을 마친 뒤 진행한다.
각 PR은 가능하면 500줄 안팎으로 유지하고, 인증 변경이 커지면 코드 교환 계약/저장소와 Route Handler/테스트를 별도 PR로 나눈다. 줄 수를 줄이기 위해 필수 검증을 생략하지 않는다.

부모 PR이 병합되면 자식 브랜치에서 부모 변경이 diff에 다시 잡히지 않도록 정리하고 base를 갱신한다. 각 PR 본문에 부모·후속 PR 링크와 해당 PR의 검증 범위를 명시한다.
전체 일정은 앱 세션 발급 방식과 최소 OS 테스트 환경을 확인한 뒤 산정한다.
Apple 계정 준비와 공증 시간은 개발 작업 시간과 별도로 관리한다.
스토어 배포를 재개할 때만 App Sandbox, 로그인 요건, 앱 가치와 심사·TestFlight 준비를 별도 계획으로 검토한다.

## 6. 참고 구현: Nexters/moa

사용자가 제안한 [Nexters/moa](https://github.com/Nexters/moa)를 읽기 전용으로 검토했다.
기준 커밋: `2a085d1614e450dc92945e1d1913aa61ae6dec6e`. 실제 앱 실행·배포 성공 여부까지 확인한 것은 아니다.

| 확인한 구현 | 우리 프로젝트 적용 방향 |
| --- | --- |
| `apps/app/src-tauri/tauri.conf.json`: Vite 빌드 `dist` 내장, 400×580 투명 메뉴바 창 | Tauri 설정 구성을 참고. 우리는 원격 Next.js 웹과 크기 조절 가능한 일반 창 사용 |
| `.github/workflows/build-app.yml`: 아키텍처별 빌드, Apple 인증서·공증 자격 증명, tauri-action, 릴리스 업로드 | Apple Silicon 한 대상으로 단순화하고 기존 pnpm·mise·Doppler 체계에 맞춤 |
| `apps/app/src/lib/check-for-updates.tsx`: 업데이트 확인·다운로드·재시작 | 일반 사용자 배포용 앱 내 업데이트의 사용자 확인과 실패 처리 흐름 참고 |
| `apps/app/src/ui/app-bar.tsx`, 약관 화면: plugin-opener로 외부 브라우저 열기 | 서비스 외부 링크를 기본 브라우저에서 여는 동작 참고 |
| `apps/app/src-tauri/src/lib.rs`: 단일 인스턴스·윈도우 상태 플러그인 | 일반 창의 재열기·포커스 처리에 맞춰 필요한 부분만 사용 |
| `apps/app/src-tauri/src/commands/auth.rs`: 외부 브라우저와 로컬 callback 서버, Apple용 서버 일회용 코드 교환 | 인증의 시작·취소·복귀 예외 흐름 참고. 현재 BFF 세션 방식을 그대로 대체하지 않음 |
| `apps/app/src-tauri/src/auth.rs`: Rust의 토큰 보관·refresh 관리 | 우리 토큰은 기존 BFF/HttpOnly 쿠키 경계에서 관리. Rust API 클라이언트로 이전하지 않음 |
| `homebrew/`, `.github/workflows/deploy-app.yml`: 릴리스 DMG와 해시로 Cask 갱신 | Homebrew를 추가하기로 정할 때 참고 |

검토 결과에 따른 범위:

- Moa는 카카오·Apple 로그인 구현이며 Google 로그인 연결을 검증해 주는 사례는 아니다. 서버 callback API도 사용하므로 백엔드 정책 확인은 계속 필요하다.
- Bun/Turborepo, 별도 앱 프런트엔드, NSPanel·메뉴바 상주·자동 실행·알림·private API 설정은 이번 요구사항으로 가져오지 않는다.
- 확인한 Tauri 설정에는 최소 macOS 버전이 명시되어 있지 않다. 이 저장소를 근거로 우리 앱의 지원 버전을 확정하지 않는다.
- 코드는 우선 구조·흐름의 참고로 사용한다. 직접 복사할 경우 해당 코드의 이용 조건과 현재 프로젝트 호환성을 먼저 확인한다.

### 추가 참고: dannysmith/tauri-template

[dannysmith/tauri-template](https://github.com/dannysmith/tauri-template), 기준 커밋 `437a18b9b63924833857f299217a5270f009d120`을 검토했다.

- `main.rs` → `lib.rs::run()` 진입점과 기능별 모듈 분리를 참고한다. Rust edition은 합의한 2024를 유지한다.
- 직접 작성한 macOS `open` 프로세스 실행은 공식 Opener 플러그인의 Rust API로 대체한다.
- 템플릿의 `recovery`는 오류 발생 시 앱 데이터를 파일에 저장하는 기능이다. 원격 웹 접속 감시가 아니다.
- Moa와 템플릿은 빌드한 React 화면을 앱에 포함한다. 우리는 기존 Next.js/BFF를 유지하고 원격 웹에 접속한다.
- 별도 `shell.html`·커스텀 프로토콜·20초 타이머를 제거해 초기 범위를 단순화한다. 최초 접속 실패의 자체 안내 UI는 제공하지 않는다는 한계를 문서화한다.
- 템플릿의 보조 창·파일 저장·다국어·광범위한 capability 설정은 도입하지 않는다. 업데이트는 기존 후속 계획을 따른다.

## 7. 공식 근거

- [Tauri 기본 프로젝트 구조](https://v2.tauri.app/start/project-structure/): 루트 JS 프로젝트와 `src-tauri/` Rust 프로젝트 구성.
- [Tauri 설정](https://v2.tauri.app/reference/config/#frontenddist): 원격 URL 로딩 지원.
- [Tauri DMG](https://v2.tauri.app/distribute/dmg/): 직접 배포 파일 생성.
- [Tauri macOS 서명](https://v2.tauri.app/distribute/sign/macos/): ad-hoc 서명·Developer ID·공증.
- [Tauri updater](https://v2.tauri.app/plugin/updater/): 일반 사용자 배포용 앱 내 업데이트.
- [Tailwind 호환성](https://tailwindcss.com/docs/compatibility): 기본 Safari 요구사항과 추가 CSS 기능의 개별 검증 필요성.
- [WebKit Safari 16.4 릴리스](https://webkit.org/blog/13966/webkit-features-in-safari-16-4/): Ventura 13.3을 포함한 제공 대상. Sonoma만 필요하다는 근거가 아님.
- [Tauri WebView 버전](https://v2.tauri.app/reference/webview-versions/): 시스템 WebKit 사용.
- [Tauri 딥링크](https://v2.tauri.app/plugin/deep-linking/): macOS 등록과 설치 번들 검증 조건.
- [Tauri 원격 API 권한](https://v2.tauri.app/security/capabilities/): 원격 웹에서 네이티브 명령 접근 제한.
- [Google OAuth 정책](https://developers.google.com/identity/protocols/oauth2/policies): embedded user-agent 인증 제한.

정책과 도구 문서는 구현 및 제출 시점에 다시 확인한다.
